# 06 — 移動之後才失去使用者

**What to build:** 讓「機器人已經走了幾步，使用者才消失」這條路徑有測試。

**這張票是 ticket 01 的盤點挖出來的，原本不在 M6 的計畫裡。** 舊 runner 的 T5 買到的性質是：**使用者一旦不見，迴圈就不再發出驅動命令**。目前套件裡每一個 `lost_user` 測試都是**還沒動就失去使用者**（`steps == 0`），走的是不同的程式路徑 —— 移動後那條會先由該次移動設下 invalidation epoch，`_fresh_median` 是拿 epoch 在濾，而不是在空的讀數歷史上濾。

`PLAN.md` §5 缺陷 E 講的正是這條路徑上「太早放棄」。M5 修的是啟動時要在 timeout 內輪詢而不是第一輪就放棄；但「移動之後失去目標要停下來」這半邊，現在沒有任何斷言。

盤點也記下了另一件事：舊的 T5 用「drive calls == 2」來表達這個性質，那是綁在舊控制律步數上的脆弱寫法。新測試要斷言的是**行為** —— 失去使用者之後不再有新的驅動命令 —— 而不是某個特定的次數。

## Comments

完成於 2026-08-23。只加測試，`misty_agent/` 未修改。

**世界的形狀由生產行為決定，不是挑方便的。** `DistancePipeline.latest_reading()` 在人走出
畫面後會**繼續提供最後一筆讀數**（帶著它原本的時間戳）直到過期，才回 `None`。所以迴圈先被
餵一筆過期讀數——它必須靠新鮮度擋掉，因為該次移動在它之後設了 invalidation epoch——之後才
完全拿不到東西。`WorldThatLosesTheUserAfterMoving` 照這個順序來。

**斷言刻意不寫步數。** 舊 T5 寫的是 `drive calls == 2`，那個數字綁在舊控制律的步長上；值得
保留的性質是「人不見之後不再有新命令」，不管前面走了幾步。測試記錄「第一次看不到人時已發出
幾個命令」，最後比對總數是否還是那個值。

**測試一寫就過，所以我對生產程式碼做了 mutation testing 來證明它會失敗。** 四個 mutation：
沿用假的最後已知距離、回報 TIMEOUT 而非 LOST_USER、沒讀數就繼續下一輪、以及移動後不更新
invalidation epoch。前三個都紅——**但既有測試也全都紅**，所以還不足以證明補上了缺口。第四個
（不更新 epoch）反而**沒有**殺到這條新測試，因為讀數最終會完全消失，epoch 更不更新都一樣。

**決定性的證據是第五個 mutation：把 `LOST_USER` 回傳的 `steps=completed_steps` 改成
`steps=0`。整個 297 條套件裡只有這條新測試抓得到。** 原因很直接——在這之前，那個 return
從來沒有在 `completed_steps > 0` 的情況下執行過，所以它帶的值從未被觀察。盤點的 Gap 2
不是理論上的分類問題，是真的沒被跑到。

盤點文件的 T5 兩列改成劃線 + 「closed by ticket 06」並指向新測試名稱。**劃線而不是重寫**，
並在檔頭補一句說明：原始的判讀是刪除舊 runner 的依據，把它改掉會讓那次刪除失去解釋。

**關於並行 session 的那份被丟棄的成果：** 它裡面也有一個同名的 `WorldThatLosesTheUserAfterMoving`。
形狀相近是預期的——它由 `DistancePipeline` 的行為決定，不是由誰先寫決定。但那份是在
`approach.py` 還掛著 mutation check 人為缺陷的樹上寫的，沒有採用；本 ticket 從乾淨的樹重寫，
並自己做了完整的 mutation testing。

驗證：`.venv/bin/python -m pytest tests/ -q -rs` → **297 passed、零 skip**（296 → 297）。
既有的兩條「啟動時失去使用者」測試未修改且仍然通過。
