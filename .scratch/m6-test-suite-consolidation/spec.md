# M6 — 測試套件收斂

Status: ready-for-agent

> 上游脈絡：`PLAN.md` §5（缺陷 B、C）、§7（里程碑 M6）、§13（M5 的結果與邊界）、
> §14（2026-08-20 的里程碑重整與 gate/report 原則），以及 `CONTEXT.md` 的術語。
> 本 spec 使用 `CONTEXT.md` 的詞彙：Step、Reading、Sweep、Measurement、Envelope。

---

## Problem Statement

M5 交付了可信的 approach 後端，但測試套件帶著三個問題進入 M7，而 M7 會把它們全部放大。

**第一，覆蓋重複而且沒有出處。** `test_sim.py` 的 24 個 scenario 大半已經被 `tests/` 裡
走 public seam 的版本涵蓋，剩下的測的是即將刪除的舊主腳本。`HANDOFF.md` 目前把「把
`test_sim.py` 遷入 pytest」寫成 M6 的工作；照字面執行會把已經涵蓋的東西再寫一遍，並把
舊主腳本的行為當成需求正式化。

**第二，M5 的驗收有一個實質缺口。** `approach()` 對 Reading 做中位數聚合，這個機制存在
的唯一理由就是抗噪 —— 而套件裡沒有任何測試餵過它噪音。`tests/`、`harness/` 與
`misty_agent/` 目前只有公分量化與延遲模型，沒有任何加性誤差。

**第三，唯一存在過的噪音模型是錯的，而且錯的方向會讓安全結論失真。** 舊的
`test_sim.py` T4 用與距離無關的均勻 ±N 公分。但距離是由 pinhole 關係從臉的像素寬推得的，
距離與像素寬成反比，所以固定的像素抖動換算成公分誤差時隨距離平方放大。在預設校正常數
下，safety floor（45cm）附近 1px 抖動只有 0.2cm，而 200cm 處是 4.1cm。均勻 ±8cm 因此在
**決定安全的近距離注入了物理上不可能的噪音**（相當於臉寬的 17%），在**偵測真正不穩的遠
距離又注入得不夠**。

這是 `PLAN.md` §12.1 與 §12.5 那條教訓的第三次現身：**量測設定必須等於生產設定**。前兩次
都是量錯了東西而不是算錯，這次是模型與生產管線的誤差結構不一致。

## Solution

把測試套件收斂到一個可以交接的狀態：每一項覆蓋都有出處、沒有重複、沒有已知缺口，而且
噪音這個從未被量過的參數，用與 transport lag **完全相同**的方式處理 —— 掃描出 Envelope
並報告，不設門檻。

三件事，順序固定：

1. **產出覆蓋盤點**，逐項寫明 `test_sim.py` 每個 scenario 在新套件裡的下落：已被哪個測試
   涵蓋、屬於 M7、或是缺口。盤點是刪除測試的依據，必須先於刪除存在。
2. **依盤點刪除整個 `test_sim.py`**，並把它帶走的覆蓋明確記錄成待重建項目。
3. **用距離相依的噪音模型擴充既有 Sweep**，量出噪音與 transport lag 交互作用下的 Envelope
   邊界，並用一個獨立的 Measurement 證明該模型與真實偵測器一致。

M6 不建立 Journal，不碰 ReAct。Journal 已於 `PLAN.md` §14 移入 M7，因為它唯一真實的
生產者是 `react.py`；用控制層的事件去驗 ReAct 層的 schema，就是同一條「量測設定必須等於
生產設定」的教訓。

## User Stories

1. 身為接手的 agent，我想看到一份逐項的覆蓋盤點，這樣我刪除舊測試時知道自己沒有一併刪掉唯一的覆蓋。
2. 身為接手的 agent，我想讓盤點指出每個舊 scenario 對應的新測試名稱，這樣「已涵蓋」是可查證的主張而不是斷言。
3. 身為接手的 agent，我想讓盤點明確標示哪些覆蓋會被刪除且不重建，這樣缺口是有意識的決定而不是意外。
4. 身為接手的 agent，我想讓盤點標明它是手寫的、不可重跑，這樣沒有人誤以為它能像量測報告一樣重新產生。
5. 身為開發者，我想刪掉 `test_sim.py`，這樣專案不再維護兩套針對同一行為、結論可能分歧的測試。
6. 身為開發者，我想在刪除前確認前進、後退、失去使用者、步數耗盡與校正誤差都仍有走 public seam 的覆蓋，這樣刪除不降低保護。
7. 身為開發者，我想讓舊主腳本的 brain 與 memory 覆蓋隨 `test_sim.py` 一起消失而不是搬進 `tests/`，這樣不會把即將被 function calling 取代的需求正式化。
8. 身為開發者，我想讓 memory 折疊與持久化的覆蓋被登記為 M7 的待重建項目，這樣它不會靜默消失。
9. 身為開發者，我想讓噪音以像素抖動為參數而不是公分，這樣模型的誤差結構與生產管線的 pinhole 關係一致。
10. 身為開發者，我想讓噪音造成的公分誤差隨距離平方放大，這樣近距離不會被灌入物理上不可能的誤差。
11. 身為開發者，我想讓加了噪音的 Reading 仍走管線既有的整數截斷，這樣模型不會比生產管線精確。
12. 身為開發者，我想讓噪音從既有的 Sweep 感知注入點進入，這樣兩個未量參數共用同一條注入路徑而不是各開一條。
13. 身為開發者，我想讓 `approach()`、`plan_step()` 與 `DistancePipeline` 在 M6 完全不被修改，這樣 M5 的證據仍然成立。
14. 身為開發者，我想把 δ_px 明列為 UNCALIBRATED 假設，這樣它與 `sensor_transport_lag_s` 的地位一致且可被讀者辨認。
15. 身為開發者，我想同時掃描 transport lag 與噪音，這樣兩者的交互作用不會因為單一切片而被漏掉。
16. 身為開發者，我想讓報告只呈現邊界曲線而不是整個掃描曲面，這樣結果仍然是一兩句話而不是一張讀不動的表。
17. 身為開發者，我想知道每個噪音幅度下最大的收斂 transport lag，這樣可以直接看出噪音把 Envelope 推移了多少。
18. 身為開發者，我想讓掃描報告 safety floor 越線之外的失敗模式，這樣不會只量到我已經想到的那一種。
19. 身為開發者，我想知道每次 approach 的方向反轉次數，這樣抵達帶邊緣的來回震盪不會被「沒有越線」掩蓋。
20. 身為開發者，我想讓反轉計數本身有一個必定反轉的測試情境，這樣計數器不會是一個從未看過目標現象的診斷器。
21. 身為開發者，我想知道收斂率而不只是第一個失敗點，這樣噪音造成的漸進退化是可見的。
22. 身為開發者，我想讓噪音 Envelope 只被報告而不設門檻，這樣專案不會對一個從未量過的量假裝有標準。
23. 身為開發者，我想讓「封閉式噪音模型與真實偵測器一致」成為有斷言的 Measurement，這樣模型與現實分歧時會被抓到。
24. 身為開發者，我想讓交叉檢查涵蓋數個距離而不只一個，這樣驗證的是隨距離變化的關係本身。
25. 身為 CI，我想讓 M6 的所有測試免費、確定性、不呼叫 LLM、不需要網路與硬體，這樣它們可以在每個 push 執行。
26. 身為 CI，我想讓 `.venv` 底下沒有任何測試 skip，這樣挑錯直譯器不會看起來像一片綠。
27. 身為 ReAct agent，我想在 M7 開始前繼承一個沒有已知覆蓋缺口的套件，這樣後續的 Journal 斷言站在驗過的地基上。
28. 身為履歷讀者，我想看到未量參數被掃描而不是被猜測，這樣專案的誠實邊界是一致地被套用而不是只用在一個參數上。
29. 身為履歷讀者，我想看到刪除測試附帶一份公開的依據文件，這樣減少測試不是靠信任而是靠紀錄。
30. 身為使用者，我想確認在合理的偵測抖動下 robot 仍不會越過模擬安全底線，這樣安全主張涵蓋的是有雜訊的世界而不只是乾淨的世界。
31. 身為接手的 agent，我想讓 M6 嚴格停在測試收斂，這樣完成後能直接進入 Journal 與 ReAct 而不帶未結的支線。

## Implementation Decisions

- M6 的唯一目標是測試套件收斂。**不建立 Journal、不建立 EventBus、不碰 ReAct、不新增工具。**
- 覆蓋盤點是一份**手寫**文件，與量測報告放在同一個目錄。檔頭必須明確標示它不是產生物、
  不可重跑；目錄裡其他文件多半是 `python -m harness` 產生的，混淆會讓讀者以為它能重現。
- 盤點必須逐項處理 `test_sim.py` 的每個 scenario，並歸類為三者之一：**已被具名的新測試涵蓋**、
  **屬於 M7**、**缺口**。歸類為「已涵蓋」時必須寫出對應的測試名稱。
- `test_sim.py` **整個刪除**，不保留殘骸。它的 brain sanitization 與 memory scenario 不遷移：
  M7 改用 OpenAI function calling，由模型端保證結構，「消毒 malformed JSON」這個需求不會
  存在；把它搬進 `tests/` 等於把一個即將消失的需求正式化，M7 還得再刪一次。
- Memory 折疊與持久化的覆蓋隨之消失，這是**有意識的缺口**。它必須同時記在盤點與 `PLAN.md`，
  並登記為 M7 搬出 memory 時的重建項目。
- 噪音從 **Sweep 現有的感知注入點**進入 —— 也就是目前注入 transport lag 的同一個地方。
  不新增第二條注入路徑。`approach()`、`plan_step()` 與 `DistancePipeline` 在 M6 一行不改。
- 噪音的參數是**像素抖動 δ_px**，不是公分。每筆 Reading 的公分誤差由 pinhole 關係推得：
  距離與臉的像素寬成反比，因此固定的像素抖動造成的公分誤差隨距離平方放大。誤差套用後
  仍走管線既有的整數截斷，模型不得比生產管線精確。
- δ_px 明列為 **UNCALIBRATED**，與 `sensor_transport_lag_s` 同級：從未被量過，沒有硬體也
  量不到。任何敘述都不得暗示它是量出來的。
- Sweep 是**二維的**：transport lag × δ_px。但**報告只呈現邊界曲線** —— 每個 δ_px 對應的
  最大收斂 lag —— 不呈現整個曲面。二維是實驗的形狀，不是報告的形狀。
- 掃描結果必須區分三種失敗模式：**safety floor 越線**、**未收斂**、**方向反轉**。前兩者
  既有結構已能表達；**方向反轉是新增的量**，因為它是噪音的特徵失敗模式，而且它不越線、
  也可能照樣回報 `arrived`，兩個既有軸對它都是瞎的。
- **噪音 Envelope 只報告，不設門檻**，與 transport lag Envelope 同級。專案的原則寫成明文：
  **Measurement 設門檻，Sweep 只報告**。延遲是量到的，所以有 2× floor bound 的硬 gate；
  transport lag 與 δ_px 是掃出來的，所以零斷言。
- **「封閉式噪音模型與真實偵測器一致」是 Measurement，要有斷言。** 在數個距離上比對模型
  預測的公分誤差與真實偵測器經合成影格產生的結果。這是模型與現實分歧時唯一會亮的燈。
- M6 的報告**另寫新檔**，不覆寫 M5 的證據報告。這沿用 `PLAN.md` §13.3 第 3 點的先例：
  M5 產物另存新檔而不覆蓋 M4 的 before-state。
- `PLAN.md` §7 的里程碑表與新增的 §14 必須同步更新，`HANDOFF.md` 的「下一步」與驗收指令
  亦然。刪除 `test_sim.py` 之後，驗收指令從三條變兩條。

## Testing Decisions

- 好測試只斷言通過公開介面可觀察的行為。不斷言注入點的內部型別、延遲線的資料結構、
  掃描的迴圈次數，或私有方法。
- **主要 seam 是既有的 Sweep 感知注入點**，也就是 transport lag 目前進入的地方。噪音共用它。
  這是本 spec 唯一被修改的 seam；不新增第二個。
- **交叉檢查走既有的合成相機與偵測器 seam**，與感知測試同一條路徑。它不是新 seam。
- 方向反轉計數**必須有自己的測試**：構造一個必定發生反轉的情境，證明計數器數得到。這是
  `PLAN.md` M4 #07 的教訓 —— 診斷器沒看過它要偵測的東西，就等於沒有診斷器。
- 掃描必須證明它涵蓋了餵給它的每一個網格點，且在任何噪音幅度下步數上限都不被突破。
  終止保證不因為新增參數而鬆動。
- 噪音模型必須有一個測試證明它**重現了餵給它的抖動** —— 與現有延遲模型用同一把尺自我驗證
  的做法一致。
- 噪音 Envelope **不得有任何斷言限制它落在哪裡**。測試可以斷言「報告說明了自己是 Sweep
  而不是 Measurement」、「邊界的定位精度有被寫出來」，但不能斷言邊界的數值。
- 覆蓋盤點的每一條「已涵蓋」主張都必須指向一個當下存在且通過的測試。盤點寫完到刪除之間，
  套件必須是綠的。
- Prior art：`tests/test_robustness.py` 的延遲模型自我驗證與 Envelope 敘述測試、
  `tests/test_latency_bound.py`（Measurement 設門檻的唯一先例）、`harness/robustness.py`
  明文的無門檻立場、`tests/test_perception_face.py` 與 `tests/conftest.py` 的合成影格與
  fixture 慣例。
- 全部 M6 測試在專案 `.venv` 執行，不呼叫 LLM、不需網路、不需硬體，且**感知案例不得 skip**。

## Out of Scope

- Journal、事件型別、EventBus、JSONL 紀錄與任何渲染器。全部在 M7。
- ReAct loop、function calling、工具註冊表、observation schema、TTS 抑制窗。
- 修改 `approach()`、`plan_step()`、`DistancePipeline` 或 `Settings` 既有欄位的**行為**。
  M6 只在 Sweep 側新增參數。
- 更換或調整臉部偵測模型、MediaPipe 參數、Tasks API 遷移，或提升辨識品質。
- 量測相機曝光、Misty 編碼、Wi-Fi 或 RTSP 的真實延遲；量測真實的偵測器抖動。兩者都需要硬體。
- 真機校準、真機安全認證、宣稱 `approach()` 曾在 Misty II 上執行。
- 重寫 memory、prompt、人格、表情、手臂、頭部、燈光與音訊。
- 刪除 `full_robot_v3.py`。它在 M7 搬完 prompt 與 memory 後才消失；M6 只刪它的測試。
- Docker、CI workflow 與 README。

## Further Notes

- 舊 T4 模型錯得多具體：預設校正常數下，均勻 ±8cm 在 45cm 處相當於約 38px 的抖動 ——
  臉寬的 17%，物理上不可能；同樣的 ±8cm 在 200cm 處只有約 2px。近處過嚴、遠處過鬆，
  而近處正是安全結論被決定的地方。這些數字應該寫進盤點，因為它們是刪掉 T4 而不是移植
  T4 的理由。
- 二維掃描在計算上便宜：Sweep 的模擬世界不跑偵測器。真正的成本在交叉檢查，而那只需要
  數個距離各跑一次，不進網格。
- **順序是這份 spec 的一部分，不是建議。** 盤點先於刪除，刪除先於新測試 —— 這樣 git 歷史
  本身就證明了覆蓋主張不是事後補的。`PLAN.md` §14 記錄了同一條紀律在 M7 的形式（schema
  先於 `react.py`）。
- 工作樹目前已有不屬於本 spec 的未提交修改（`.env.example`、`architecture.svg`、
  `docs/measurements/m4-harness-report.md`、`tests/conftest.py`）。全部保留；提交時用明確
  檔案清單 stage，不要用 `git add -A`，並先檢查 `git diff --cached --stat`。
- 本 spec 完成後用 `/to-tickets` 拆成少量 tracer-bullet tickets。M6 收尾後直接進 M7，
  不新增支線。
