# 08 — `sensor_transport_lag_s` 魯棒邊界掃描

**What to build:** 一張圖或一張表,回答「相機到 process 之間再多幾百毫秒的延遲,
這個控制律還收斂嗎?」

這一張處理的是**永遠量不到的那一段**。整條鏈路可以切成兩截:

```
[真值] ─ 曝光 → 編碼 → RTSP over WiFi ─▶ [進 process] ─ 緩衝/偵測/濾波 ─▶ [回報距離]
        └────── 截段 A:需要硬體,量不到 ──┘  └────── 截段 B:06/07 量的就是這段 ──────┘
```

截段 A 需要實機,而本專案永久沒有實機(`PLAN.md` §1)。誠實的做法不是去猜一個數字,
而是**承認它未知,然後證明控制律在多大的未知範圍內仍然可用**。這比單點數字更有說服力,
而且是無硬體條件下能做出的最強結果。

`sensor_transport_lag_s` 這個 config 欄位在 M2 就已經宣告並標為 UNCALIBRATED,但至今
沒有任何東西讀它。這一張讓它第一次真的有作用:harness 注入影格時額外延遲這麼多,
模擬截段 A。

掃描的取向沿用 `tests/test_step_policy.py` 的做法:**掃真的函式,不要推公式**。M2.5
的教訓是手推閉式解會在無人察覺的情況下算錯(`PLAN.md` §10 第 1 項)。

**Blocked by:** 06(需要延遲量測機制)

**Status:** ready-for-agent

- [ ] harness 能依 `sensor_transport_lag_s` 的設定值,在注入影格時加上對應的額外延遲
- [ ] 掃過一段範圍,對每個值記錄控制律是否收斂到抵達帶、用了幾步、最近距離多少
- [ ] 輸出魯棒邊界:控制律仍收斂的範圍,以及超過之後怎麼壞的(震盪?超衝?步數用盡?)
- [ ] 結果明確標註為**參數掃描,不是量測**——這個數字沒有任何實機依據
- [ ] 掃描以驅動真實控制律為之,不另行推導閉式解
- [ ] 掃描本身不掛門檻(收斂範圍是要報告的事實,不是要通過的標準)
- [ ] `pytest` 與 `test_sim.py` 兩套除 06 的刻意紅之外全綠
